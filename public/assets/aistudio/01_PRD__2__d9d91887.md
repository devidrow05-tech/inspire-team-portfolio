## 1. Executive Summary

Inspire Team is a private-plus-public web platform for an academy that runs a professional digital team (web, Android, design, WordPress, e-commerce, video, marketing). The owner (admin) assigns work, members submit finished projects, the admin reviews every submission, and **only admin-approved projects become public**. Visitors browse a polished public portfolio without an account. Members also get a built-in browser-based **multi-image-to-PDF converter** to keep storage small.

It is a team operations + assignment management + review workflow + secure file management + public portfolio platform — not just a portfolio site.

## 2. Vision, Problem, Objectives

**Vision:** One trusted place where every piece of team work is organised, reviewed by the owner, and showcased professionally.

**Problem:** Completed projects are scattered, not reviewed consistently, and cannot be showcased publicly in a controlled way. Assignments, files and feedback live in chats and folders.

| # | Business objective | Product goal |
|---|---|---|
| BO-1 | Owner controls everything public | Approval-gated publishing; admin-only publish |
| BO-2 | Organised team work | Assignment module with per-member progress |
| BO-3 | Professional public image | Bilingual (EN/UR), responsive, SEO-ready portfolio |
| BO-4 | Low storage cost | Client-side image→PDF, 10 MB file cap, quotas |
| BO-5 | Accountability | Audit log of every significant action |

## 5. Users & Personas

| Persona | Description | Key needs |
|---|---|---|
| **Owner / Super Admin** | Academy owner | Control, visibility, approvals, audit |
| **Team Member** | Developer/designer/editor | See tasks, submit work, get feedback, build portfolio, shrink image sets into PDFs |
| **Visitor** | Prospective student, parent, client | Trust: see real, approved work; contact the academy |

**Journeys (summary).**
1. *Admin:* login + MFA → create member → create assignment → member submits project → review → approve & publish → appears publicly.
2. *Member:* first login → change password → accept assignment → create project draft → build PDF from images → upload → submit → read feedback → resubmit → see it live.
3. *Visitor:* homepage → team directory → member portfolio → project detail → WhatsApp/contact.

## 7. Business Rules

| ID | Rule |
|---|---|
| BR-01 | Only role `admin` can publish, unpublish, feature, archive or restore projects. |
| BR-02 | No member action can make content public. Public visibility = a row in `published_projects` with `is_visible = true`, created only by `admin_publish_project`. |
| BR-03 | Public pages read **only** published snapshot tables; working copies (`projects`) are never public. |
| BR-04 | A published project's live snapshot never changes when a member edits; edits happen in the working copy and go through a new review cycle. The old live version stays visible until the replacement is approved. |
| BR-05 | Assignments are private. Public exposure only through `public_showcases`, a separate admin-authored record containing only fields the admin typed for public display. |
| BR-06 | Members see only their own projects, assignments they are assigned to, and their own notifications. Collaborators are display credits only and get **no** private access. |
| BR-07 | Member profile content is admin-controlled; members submit `profile_change_requests`. |
| BR-08 | Every status change, approval, publication and file operation writes an `audit_logs` row; no one can edit or delete audit rows through the app. |
| BR-09 | Files are private by default. Only the Publish Gate copies approved files to the public bucket. |
| BR-10 | External URLs must be `http(s)` only. |
| BR-11 | Suspended/deactivated accounts lose all data access immediately; their public profile is hidden; their published projects stay visible (name as plain text) unless admin unpublishes. |
| BR-12 | Images converted to PDF are not stored unless the member explicitly ticks "also save original images". |
| BR-13 | Draft projects can be soft-deleted by their owner; submitted/published ones only by admin (archive). |
| BR-14 | Per-file limit 10 MB; per-member storage quota default 200 MB; total storage warning at 80% of configured quota. |

## 9. Project Status Machine

| From | Action | To | Actor | Side effects |
|---|---|---|---|---|
| — | create | draft | member | version_count = 0 |
| draft | `submit_project` | submitted | member | snapshot version n; notify admin; audit |
| submitted | `withdraw_submission` | draft | member | only before review starts |
| submitted | `admin_start_review` | under_review | admin | audit |
| under_review | `admin_publish_project` | published | admin | files copied, live row upserted, notify member |
| under_review | `admin_request_changes` | changes_requested | admin | feedback required; notify |
| under_review | `admin_reject_project` | rejected | admin | reason required; notify |
| changes_requested | `submit_project` | submitted | member | new version |
| published | `start_project_revision` | draft | member | live row stays visible |
| draft (revision) | `withdraw_project_revision` | published | member | working copy restored from live snapshot |
| published | `admin_unpublish_project` | draft | admin | live row hidden |
| any except archived | `admin_archive_project` | archived | admin | live row hidden; previous status saved |
| archived / rejected | `admin_restore_project` | previous status / draft | admin | live row stays hidden until `admin_republish_project` |
| hidden live row | `admin_republish_project` | (unchanged) | admin | `is_visible = true` |

**Visibility rule:** the *status* describes the working copy. Public visibility depends **only** on `published_projects.is_visible`. A project in `draft` that has a live snapshot (revision in progress) therefore remains visible with its last approved content.

## 11. Security & Privacy Requirements

| ID | Requirement |
|---|---|
| SEC-001 | RBAC via `profiles.role`; privileges enforced server-side (RLS, RPC, Functions) — never only in UI. |
| SEC-002 | RLS enabled on **every** table in `public`; `anon` gets SELECT only on public-safe tables. |
| SEC-003 | Service-role key exists only in Cloudflare Function secrets; never in `VITE_*`, repo or logs. |
| SEC-004 | Members cannot write columns `status`, `role`, `owner_id`, `live_version_id` (guard triggers + RPC-only transitions). |
| SEC-005 | IDOR-safe: every private read filtered by `auth.uid()` ownership or admin. |
| SEC-006 | XSS: no `dangerouslySetInnerHTML`; markdown rendered without raw HTML; URL allow-list. |
| SEC-007 | Security headers + CSP via `public/_headers`. |
| SEC-008 | Contact form: honeypot, length limits, IP-hash rate limit (default 5/hour), optional Turnstile. |
| SEC-009 | Admin MFA + aal2 in RLS for admin policies. |
| SEC-010 | Audit log immutable (no UPDATE/DELETE policies; revoke from app roles). |
| SEC-011 | Private routes `noindex` + `Disallow` in robots. |
| SEC-012 | Secure external links: `rel="noopener noreferrer"`; no iframes of third-party content. |

**Mandatory authorization tests (must pass before launch):**
1. Member A changing a project/file/assignment ID in URL or API cannot read Member B's data.
2. Member calling any `admin_*` RPC or `/api/admin/*` Function receives 403.
3. Member cannot insert/update `published_projects` or set a project to published via direct PostgREST request.
4. Anonymous visitor cannot fetch a private file by guessing its path or listing the bucket.
5. Suspended member's valid JWT returns no data.
6. Admin without AAL2 cannot run admin writes.

## 13. Acceptance Criteria (Given / When / Then)

| ID | Scenario |
|---|---|
| AC-001 | **Given** an invited member **When** they log in the first time **Then** they must change the temporary password before reaching the dashboard. |
| AC-002 | **Given** a member with a draft **When** they submit **Then** status = submitted, a version row exists, admin gets `project_submitted`, the project is not public. |
| AC-003 | **Given** a project under review **When** admin approves & publishes **Then** a `published_projects` row exists, files exist in `public-media`, the member is notified, and the project appears in listings and on the member profile. |
| AC-004 | **Given** a published project **When** the member starts a revision and edits **Then** the public page still shows the old content. |
| AC-005 | **Given** a revision submitted **When** admin approves **Then** the public page updates to the new version and the older version stays in history. |
| AC-006 | **Given** admin requests changes **When** the member opens the project **Then** admin feedback is visible, internal notes are not. |
| AC-007 | **Given** a visitor **When** they open `/projects` **Then** only `is_visible = true` rows appear and no private field is in the network response. |
| AC-008 | **Given** a member **When** they call `admin_publish_project` directly **Then** it fails with 403/permission denied. |
| AC-009 | **Given** a member **When** they request another member's private file URL **Then** access is denied. |
| AC-010 | **Given** 5 images **When** the member generates a PDF (A4, Balanced) **Then** one PDF downloads, no originals were uploaded. |
| AC-011 | **Given** a generated PDF larger than the limit **When** the member tries to upload **Then** upload is blocked with a message offering a smaller preset. |
| AC-012 | **Given** an assignment with 2 members **When** one marks blocked **Then** assignment status = blocked and admin is notified. |
| AC-013 | **Given** an assignment **When** it is not in `public_showcases` **Then** no assignment data is reachable by anon. |
| AC-014 | **Given** Urdu selected **When** any page renders **Then** `dir="rtl"` and mirrored layout apply with no overflow. |
| AC-015 | **Given** a suspended member **When** they use an existing session **Then** all data requests return empty/denied and the UI signs them out. |
| AC-016 | **Given** an admin without MFA **When** they log in **Then** they can only reach MFA enrolment. |
